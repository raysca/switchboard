# Pipecat parity matrix

Reference: `pipecat-impl/` @ `2967e1c09ad484076089bc88427d305fe8f79fa9`. Pipecat paths are relative to `pipecat-impl/src/pipecat/`; Switchboard paths to the repo root. Scope: a robust, fast, scalable voice server. Out of scope: video, new transports, the `pipecat-flows` Python DSL (Switchboard has its own stored step/route flows; see the Flows row), bus and multi-worker flows, speech-to-speech. This is the "Pipecat behavioral parity" surface of `docs/pipecat-compatibility.md`; it says nothing about RTVI client or Whisker conformance.

Last checked 2026-10-22 against `main` at `82d8bbf`: defaults, statuses and cited paths/tests were re-checked against the code (TestParityMatrix enforces paths, tests and declared differences only); prose details may lag. Benchmark and live-provider figures come from the cited pages and were not re-run.

**Status**: `parity` = same observable behavior on the paired fixtures or tests cited; `partial` = a real subset, or same behavior with the gaps listed; `intentionally different` = deliberate other design (or a Switchboard-only addition); `not planned` = not built, no plan to; `planned (hook exists)` = the Go hook is in the tree and tested, nothing in the server reaches it yet; `parked` = kept for a documented deliverable, not on a call path.

**Default**: whether a stock server runs it. `on`, `off` (and what enables it), `library only` (no config reaches it), or `n/a`. Most turn-taking rows run under the turn manager (`turn.manager`, on by default); per-flow settings live in the stored flow config, everything else is server-wide YAML (`server/config.go`).

**How rows are checked.** Rows marked *paired* run the same scripted input through Pipecat (executed from `pipecat-impl/.venv`) and Switchboard; goldens are in `tools/compat/testdata/parity/`, 61 scenarios in 10 areas, 15 with a declared `intentional_difference` (each one named in a row below as `area/scenario`). `go test ./tools/compat/...` compares against the goldens without Python; `make parity-regen` re-executes Pipecat. A fixture checks one component on scripted frames, not a live call. `TestParityMatrix` fails if a path or test cited here is missing, a status or default is invalid, or a declared difference is not explained in this file.

## Known gaps and risks

Re-checked against the code at `82d8bbf` (after the review remediation). Items fixed since the earlier list are removed.

- **Turn manager is on by default** (`server/config_defaults.go`, `vad.stop_ms` 200); `turn.manager: false` restores raw VAD-stop turns. A flow can set its own end-of-turn timing and strategy. The default stop costs about +0.6 s voice-to-voice in the Google live check (`docs/benchmarks/turn-manager-live.md`). Still missing: one server-level test that covers barge-in over speaking TTS and the silence end together.
- **Smart Turn v3.2 misjudges clips (model, not our window).** The recorded "What is two plus two?" scores incomplete and TTS fragments score complete, in Pipecat's Python too; the audio-window bug is fixed. Not recommended until evaluated on real conversational audio (`docs/benchmarks/turn-manager-live.md`). Flows can opt into it when `turn.analyzer.for_flows` loads the model.
- **`chirp_2` sends no interim results**, so `turn.min_words` (server-wide or per flow) gives no barge-in until its final (about 1.5 s after speech); `latest_long` has interims. A WARN and `voice_turn_min_words_no_interims_total` flag it once per call.
- **NIM reasoning-only models.** The OpenAI processor cannot pass `reasoning_effort` or `chat_template_kwargs`; reasoning models (nemotron-3-super, nemotron-3.5-lightning) have first tokens of 0.7 to 6 s or worse. Default openai/gpt-oss-20b; NVIDIA's model list includes models that answer 404/410 for the account (reported as a non-retryable client error telling the operator to set the model).
- **STT breaker pattern is half unified**: Deepgram, Cartesia, ElevenLabs and Nvidia Riva STT run on the shared `core/sttunit` runner, which owns their `WouldRefuse` gate, Report and RecordSuccess; Google and xAI STT keep their own schedulers and breaker calls. xAI STT counters are still not exported (only its circuit-state gauge is).
- **Unbound-interim false failover (risk, inferred from code, not seen live).** Words an STT reported between turns as a non-final interim are owed by the next turn; a provider that never finalizes them (Riva may answer a half-close with nothing) makes the turn look lost, invalidates it and fails over or demotes the provider for the call (`core/sttunit/runner.go`, `lost()`). An unbound final is safe (`TestRunner_UnboundFinalThenSilentEndIsNotALoss`).
- **`PingMaxFailures` has no YAML key** (fixed at 2 consecutive missed pings); only `limits.ping_interval` and `limits.ping_timeout` are configurable.
- **An abandoned browser tab holds its slot** until `limits.max_call_duration` unless `idle.user_timeout` is set; a tab that still answers pings is not dropped. The built-in default now sets a 15 s user timeout with 2 prompts, and `config/production.yaml` sets 30 s; a flow can replace it, and `0s` turns it off.
- **TTS streaming.** xAI (WebSocket, one connection per reply) and Google Chirp 3 HD voices (StreamingSynthesize, one stream per unit) emit audio as it arrives; other Google voices stay unary and synthesize up to 2 units ahead while earlier units play (`ttsunit` look-ahead). A failed stream retries as the unary request. Kill switches: `providers.google_tts.disable_streaming`, `providers.xai_tts.disable_streaming`. Not built: token-level input streaming, xAI word timestamps, look-ahead for streamed units. Live S9 (2026-10-11, n=1, not re-run): xAI 1 request instead of 12 and first audio 2.58 s (was 4.07 s); Google first audio 3.02 s (was 6.35 s) with no gaps (was 5).
- **TTS look-ahead is lost behind fallbacks**: `TTSFailover` hands its candidate one unit at a time (`core/tts_failover.go`), so a call with a TTS fallback gets no unary Google look-ahead and pays each unit's synthesis serially. The comment there saying this costs no latency is stale.
- **xAI STT ordering and drops (fixed):** `audio.done` is written after the audio buffered before `transcript.created`, and a connection drop mid-utterance or after `audio.done` with an open utterance raises a transcript-invalidating error so STT failover replays it (`TestSTTFailoverInvalidatingDropAfterSpeechFinalCommitsOnce`; the shared runner raises the same invalidation for the sttunit providers). The S2 (barge-in) and S4 (mid-utterance pause) rows in `docs/benchmarks/agent-matrix.md` are stale and have not been re-run live.
- **Cost estimates are an upper bound, actuals are measured**: live harnesses cap on measured provider requests (`voice_provider_requests_total`; Google LLM in Vertex mode is not on the shared pool and not counted there). The estimate formulas are calibrated on one xAI run and should be refreshed from the est-vs-actual table.
- **Real-provider coverage**: Google, Nvidia and xAI were run live (small n); Cartesia, ElevenLabs and Deepgram were not.
- **Eager stop has no speculation gate** and no retraction; use only with punctuating STT.
- **Failover timing and residuals.** First-token watchdog `failover.llm_first_token` 8 s with fallbacks, total `failover.llm_budget` 60 s; Google and xAI STT open is 2 attempts of 5 s (Deepgram 3 x 5 s when it is the last candidate); non-last STT/TTS candidates get at most 2 attempts (STT opens capped at 5 s each). Still open: a primary that has started streaming is bounded only by the provider request timeout (30 s for the whole LLM stream, per round); reasoning models whose first token exceeds 8 s need a raised `llm_first_token`; the breaker can open after 5 watchdog cancels; a TTS cascade of more than 3 units finishing inside one re-entry loses the oldest unit's tail frames (stopped, usage, tail error). xAI STT exports no counters.
- **Abandoned tool executors**: an executor that ignores cancellation is left running after a 1 s grace (`core/tools/loop.go`), outside the session supervisor and unbounded in count; the MCP executor honours ctx, so the risk is for custom executors.
- **Library-only code**: `ValidateToolPairing` is a test oracle in `core/coretest` (allowlisted for the dead-code gate), not server code. `SetSystemInstruction` and `SetSystemInstructionChecked` (`core/context.go`) are reached only by tests. `make deadcode` does not flag them, even with its filter widened to every workspace module: the tool counts them as reachable, so the parity-matrix row, not the tool, records them.
- **Summaries**: token usage not attributed, no output-token cap, and no pause after a discarded summary (the 30 s retry pause follows only a failure).
- **Redaction**: DTMF digits reach the client's user-transcription frame and the LLM context by design (the full alphabet, A to D included, is redacted elsewhere); digit-run and IBAN rules are heuristics. Trace spans record only the Go error type (`%T`), not the message. Store errors and most recovered panic values are redacted. Raw text remains at `server/call.go` ("turn not recorded" log), `server/recording.go` ("call recording not saved" log), and in three recovered panic values: `core/session.go` (processor panic: `%v` of the value plus stack, which becomes the session's failure cause), `transport/ws/pacing.go` and `server/demo_api.go` (the returned error carries `%v` of the value). Google STT `endTrace` only receives fixed strings today (checked), so that site is safe unless a caller changes.
- **Call-setup panic residuals**: a panic between the `activeCalls` insert and the done goroutine (`server/server.go`, for example inside `s.live.Put`) leaves an `activeCalls` entry (near-unreachable); after registration, panics belong to `finishCall`.
- **Silent VAD worker restarts**: a hung worker is killed and respawned with only the worker hang and error counters to show it (`vad/worker_executor.go`); successful respawns are not logged. Spawn, handshake and pipe (crash) failures log with stderr; hangs and found-down workers do not.
- **Scripted lines yield to model turns**: a `Say` refused while a model reply runs (`ErrSayBusy`) is counted (`GreetingFailedTotal`) and WARN-logged for the greeting and retried for idle prompts; a line accepted then overtaken by a model turn is dropped with a debug log only. Cues are sounds, not `Say` lines.
- **Recording** is unencrypted at rest (local files 0600 in a 0700 directory), taps audio at the transport before the filter chain (unfiltered inbound), a mid-call flow disable does not stop it, and no disclosure is played to the caller: the flow only has to set `recording.disclosure_confirmed`.
- **Unmeasured with real providers**: warm-up gain, real STT/LLM/TTS latency (baselines use simulated provider delays and no audio corpus; the live Google baseline is open), smart-turn and completion quality, denoiser false-barge-in rate on noisy audio (the noisy-corpus acceptance check is unmet). Deepgram, Cartesia, ElevenLabs and generic OpenAI-compatible defaults come from docs and fakes, not live APIs (Google, Nvidia Riva STT/TTS and NIM, and xAI STT/TTS/LLM were run live, small n). Google gRPC burst-replay for STT failover is unverified.
- **Admission is reject-only**: no queueing or weighted fair share.
- **Capacity**: 384 sessions clean in the latest sweep on a busy laptop (it predates the echo provider and was not re-run); one earlier run lost all workers to an unexplained stall; a residual in-flight paced frame can still delay a caller chunk. A client that stalls an RTVI write ends as `slow_client` within 1 s. A 24 h soak is not planned (calls last 2 to 3 minutes). Churn evidence is one 90 s container run (68 calls, echo provider); a longer churn at real call lengths, and with real providers, is still open.
- **ONNX Runtime exit abort.** A rare abort at exit ("recursive_mutex lock failed") is attributed to ORT's telemetry thread racing static destructors. Telemetry is now disabled (`ORT_DISABLE_TELEMETRY=1`, set in `vad/silero.go` before the ORT env exists, passed to workers by `WorkerEnv`). `vad.ShutdownORT` runs after the ORT sessions close on the clean exit paths of `cmd/server`, `cmd/vadworker`, `cmd/turnworker` and the `vad`, `smartturn` and `server` test mains; it is skipped on `os.Exit`/`log.Fatal` error exits (worker handshake failures, server start failures); the cause is plausible but unproven, and the Linux build is unverified. Privacy note: ORT telemetry (uploads to a Microsoft endpoint) was found active in the VAD workers before this fix.
- **Perf gate**: the `darwin-arm64-12c` loadtest baseline was regenerated on the echo provider in `1bc752b` (the JSON records no revision, so the commit is the record); the bench baseline dates from 2026-10-07. Neither was regenerated after the review remediation's hot-path changes. `perf-gate.yml` is advisory with no recorded run, and `docs/benchmarks/README.md` still says the baseline must be regenerated once the tree is committed (out of date).
- **Goroutine-leak checks are partial**: goleak runs in `core/sttunit`, `core/ttsunit`, `transport/ws`, `vad` and `server` only; the other packages that start goroutines are listed in AGENTS.md.
- **Assumptions still unconfirmed**: extra vendors were chosen without an answer to the open vendor question; denoiser open-source first; recording storage local only (`core/record` has only a local sink).
- **Different Silero model file** from Pipecat's bundled one; VAD decisions are not compared.
- **Coverage of this matrix**: paired fixtures cover turn start/stop timing, mute, idle, DTMF aggregation, sentence splitting, interrupted-reply content and summarization cut points, each on one component with scripted frames; the RTVI goldens pair the function-call messages and bot-tts-text with Pipecat and the pinned client. Tool-loop ordering, async tools, failover, VAD, filters, observability and operations rows are evidenced by Switchboard tests only.
