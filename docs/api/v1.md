# Management API v1

The Server registers `/api/v1/*` only on the admin listener. The public listener keeps `/health` and `/ws`; it does not expose management routes. Versioned paths and JSON fields are stable within v1. Future incompatible changes use a new path version. Persistent flow routes are provided by `api.NewAgentsHandler` and are mounted behind the existing management authentication boundary. The flow store is mandatory: the server refuses to start without `storage.dialect` (`sqlite` or `postgres`), the DSN in `GOVOICE_DATABASE_DSN`. Provider secrets come from the environment only ([providers.md](../providers.md)); no route accepts or returns them. Calls run stored flows only; YAML `pipelines:` is rejected at startup.

Set `management.api_key_env` in deployment YAML (default from `DefaultConfig`: `GOVOICE_MANAGEMENT_API_KEY`) to the name of an environment variable containing a unique, random key of at least 32 bytes. Send `Authorization: Bearer <key>` over a protected admin listener. The key is hashed at startup and compared in constant time. If the environment variable is absent, management routes return 503. The key must differ from the voice signing secret. Deployment must protect the admin listener with TLS or an equivalent trusted proxy/network boundary. Existing admin diagnostics (`/health`, `/ready`, `/metrics`, `/debug/timeline`) retain their V1 listener behavior and are outside `/api/v1`.

Responses use `{ "data": ... }` on success. Errors use `{ "error": { "code": "...", "message": "...", "request_id": "..." } }`; `details` is optional. Every management response includes `X-Request-ID`; error IDs match the header. Responses set `Cache-Control: no-store`. Auth errors never echo credentials or request bodies. POST/PUT/PATCH accept only `application/json` (parameters such as charset allowed), one JSON object, known fields, and at most 64 KiB. List endpoints may use `limit` (default 50, range 1–100) and `offset` (default 0, nonnegative).

| Method | Path | Request | Response |
|---|---|---|---|
| GET | `/api/v1/server-config` | none | `data`: `profile`, `max_sessions`, `max_call_duration_seconds`, `voice_token_max_lifetime_seconds` |
| GET | `/api/v1/operations/status` | none | `data`: `uptime_seconds`, `started_at`, `profile`, `active_sessions`, `max_sessions`, `capacity_utilization`, `sessions_total`, `turns_total`, `errors_total`, `database`, `vad`, `health` |
| POST | `/api/v1/voice-tokens` | `{ "principal": "user-id", "flow_id": "<flow id>" }` | 201 `data`: `token`, `expires_at`, `scope`; 404 unknown flow; 409 `flow_not_ready` |
| GET | `/api/v1/flows` | optional `limit`, `offset` | `data`: flow array |
| POST | `/api/v1/flows` | `{ "name", "description", "enabled?", "config" }` | 201 `data`: created flow and current immutable version |
| GET | `/api/v1/flows/{id}` | none | `data`: flow, current version, readiness |
| PUT, PATCH | `/api/v1/flows/{id}` | optional mutable fields and/or replacement `config` | `data`: updated flow; changed config publishes the next immutable version |
| POST | `/api/v1/flows/{id}/archive` | none | `data`: `{ "archived": true }` |
| POST | `/api/v1/flows/{id}/duplicate` | optional `{ "name" }` | 201 `data`: new flow with a copied configuration |
| PUT | `/api/v1/flows/{id}/mcp-tools` | `{ "tools": [{ "mcp_server_id", "remote_name", "schema_hash", "required" }] }` | `data`: newly published immutable flow version; empty array removes all current selections |

Flow configuration must be a JSON object using schema v2. Unknown fields and wrong types are rejected. A flow is attached to a set of providers when it is created or updated: every stage must name a `provider` whose variables are set in the server's environment for that service, otherwise the request fails with `400 flow_not_attached` listing the problems (`missing_stt`, `missing_credential_llm`, `unsupported_provider_tts`, ...). There is no `credential_id`: a config that carries one (on a stage, a fallback or a step) is rejected with `400 invalid_request`.

**Steps and routes.** `config` may list steps instead of being a flat stage config: each step has its own instructions, model, voice and tools, and routes (plain-language conditions the LLM acts on) move the caller between them. A config with a top-level `steps` key has steps; anything else is the flat form, which keeps working unchanged and reads as a one-step flow. Versions stored before the rename used `entry`/`nodes`/`edges`/`handoff_cue`; the server still reads those keys (on input too), but a config that mixes old and new keys is rejected.

```json
{
  "start": "front",
  "steps": [
    {"id": "front", "name": "Front desk", "config": {"stt": {...}, "llm": {...}, "tts": {...}}, "position": {"x": 0, "y": 0}},
    {"id": "sales", "name": "Sales", "tools": ["<mcp_server_id>/<remote_name>"], "config": {"llm": {...}, "tts": {...}}}
  ],
  "routes": [{"id": "e1", "from": "front", "to": "sales", "condition": "The caller wants pricing or to buy."}],
  "route_cue": {"name": "chime", "after_ms": 300}
}
```

Each step `config` is the flat stage config. Flow settings (`stt`, `vad_stop_ms`, `stt_p99_ms`, `recording`, `context`, `async_tools`) belong to the `start` step only; other steps set `llm` and `tts`. Each route becomes a `transfer_to_<step name>` tool on its source step whose description is the `condition`; calling it moves the call to the target step, keeping the conversation history. A step exposes only the MCP tools it lists in `tools`, a subset of the tools selected on the flow version. Limits: 8 steps, 32 routes, step names unique after lower-casing, one route per ordered step pair, 10 routes taken per call. Invalid flows fail with `400 invalid_config`; a step whose provider is not available fails with `400 flow_not_attached` and the step id prefixed to the problem (`sales:missing_credential_llm`). A call pins the whole flow through its flow version, so republishing never changes a live call. `route_cue.name` refers to a server-configured sound (`audio.cues`).

```json
{
  "stt":     { "provider": "google", "model": "chirp_2", "language": "en-US" },
  "llm":     { "provider": "google", "model": "gemini-2.5-flash", "system_prompt": "..." },
  "tts":     { "provider": "google", "voice": "en-US-Chirp3-HD-Aoede" },
  "context": { "max_messages": 64, "max_tokens": 8000 }
}
```

`context` is optional; unset limits default to 20 messages and 4000 tokens, and `max_messages` must be at least 2 when set. Each stage needs a `provider`; `llm.model` is required, while `stt.model` and `tts.voice` fall back to the provider's defaults. `llm.system_prompt` is at most 32 KiB. Each stage uses the provider's key from the environment, read when the call starts. If a variable is later removed, readiness turns `not_ready` with `missing_credential_<stage>` and lists the variable names in `readiness.missing_env`. Providers and the services they offer come from the catalog; `GET /api/v1/providers` lists what the running build and environment support. A model or voice the catalog does not list is still accepted.

Object keys are canonicalized before hashing; the lower-case SHA-256 hash covers only canonical configuration bytes. Each accepted config update creates the next contiguous version number atomically with mutable-field changes and never rewrites an earlier version. Readiness reasons are bounded safe codes and never include config values: `missing_stt`, `missing_llm`, `missing_tts`, `invalid_config`, `unknown_provider_<stage>`, `unsupported_provider_<stage>`, `missing_credential_<stage>` (with `missing_env`), `disabled`, `archived`, `readiness_unavailable`, where `<stage>` is `stt`, `llm` or `tts`. Only flows in `ready` or `ready_with_tool_warning` can take calls. There is no V1 pipeline import route.

Readiness includes bounded MCP states: `needs_tool_review` for schema drift/disappearance, `tool_dependency_unavailable` when a required server is disabled/unavailable, and `ready_with_tool_warning` when an optional selection is unavailable. These reasons never include config or tool values. The flow handler is constructed with the persistent `flow.Service` and must be mounted only after the outer handler has authenticated the management bearer key. Each call pins the flow's current version when it starts: it captures the selected MCP tools, persists a session row with the version ID and config hash, and ends that row on hang-up. Historical lookup uses `ResolveSession`, so later edits cannot change that session's configuration.

The server-config projection is read-only and excludes token signing keys, management keys, environment variable names, provider credentials, system prompts, and raw YAML. The voice-token request requires a 1–128 byte `principal` and a 1–128 byte `flow_id`. An unknown flow returns 404 `not_found`; a flow that cannot take calls returns 409 `flow_not_ready` with its readiness in `error.details`. The legacy `pipeline` field is rejected with 400 `invalid_request`. The token carries an `flow_id` claim; `/ws` has no `pipeline` query parameter. Issued JWTs use HS256, the configured voice issuer/audience and effective key ID (`v1` when omitted in production), a random `jti`, `scope=voice:connect`, and a lifetime capped at 60 seconds and the configured maximum. JWT times use whole seconds; nonzero `token.max_lifetime` must be at least two seconds and issuance rounds down to a whole second to remain within that maximum. They are intended for the existing `/ws` admission flow, which consumes each `jti` once. A voice token cannot authenticate `/api/v1`; a management key cannot authenticate `/ws`.

Providers are read-only:

| Method and path | Purpose |
| --- | --- |
| `GET /api/v1/providers` | Every catalog provider: `id`, `display_name`, `detected` (any of its variables set), `env` (the variable names it reads), `capabilities` (available services) and `services.{stt,llm,tts}` with `available`, `reason` (`missing_env` or `not_in_build`), `missing_env` (variable names), `models`, `voices`, `languages` and `custom` (whether free text is offered). Names only, never values. |

Any other path under `/api/v1/providers/` returns 404; the earlier `/api/v1/providers/credentials` routes no longer exist. Set or change a provider key by editing the server's environment and restarting ([security/credentials.md](../security/credentials.md)).

API-issued scoped tokens include a random `issuer_epoch` generated by their validator instance. Replacing that validator rejects every earlier scoped token even while it is unexpired, closing the in-memory replay-cache restart gap. A deployment with multiple Server replicas must route token issuance and the corresponding `/ws` admission to the same replica. Cross-replica use requires a shared replay/issuance service in a later task. Compatibility: the V1 WebSocket validator continues to accept its historical unscoped admission tokens, while rejecting any explicitly scoped token other than `voice:connect`. A call still needs an `flow_id` claim, so a token without one is admitted but the session fails to start. Operators can therefore migrate token issuers without breaking existing clients. Removing unscoped acceptance requires a separately coordinated protocol change. The currently configured voice signing key remains the signing key for both legacy and API-issued voice tokens; the management key is separate and never signs voice tokens.

`/api/v1` and noncanonical `/api/v1/...` paths return the same JSON error envelope with `X-Request-ID` and `Cache-Control: no-store`, without an automatic slash redirect. The body limit counts the full request body, including trailing whitespace and any second JSON value.
