## Rulings (mine; recorded in the ledger; the reviewer may challenge them)

- **R1 UI only where the server is done.** No REST or storage change in this phase. A task that finds the server contract wrong stops and reports (it is a bug for its own task, not a UI workaround).
- **R2 zod mirrors the server, never stricter.** New schemas use `.optional()` for fields the server omits (`omitempty`) and never `z.enum` on values the server may extend (e.g. readiness reasons stay `z.string()`); the live-call response is parsed as `{ data: { accepted: number } }` exactly as `server/live_calls_api.go:27-29,82` sends it.
- **R3 Live-call controls (B1) are minimal and safe.** One note per request (the API takes up to 8; nobody needs batching from a text box), a "Reply now" checkbox mapped to `run` (default **off**, as the API), and an "Ask for a reply" button (`POST .../run`). Shown only while `session.status === "active"`. Notes live in component state only: cleared on success, never in the URL, `localStorage`, a query key, the mutation cache (the `useMutation` closes over the `note` state and takes no variables, since TanStack keeps mutation variables in the `MutationCache`), or `console`. The help copy says what is kept: "The note itself is not saved; the agent's reply is." (the reply is a stored turn; the note text reaches only the in-memory history). `maxLength={4096}` counts UTF-16 units while the server counts bytes: a multibyte note near the limit gets the server's 400 message, shown as is. No auto-retry on 429/409 (the operator retries; `Retry-After: 1`). Error copy per status: 400 server message, 404 "The call has ended, or it runs on another server instance.", 409 "The call is still starting. Try again in a moment.", 429 "Too many requests for this call. Wait a second and try again." A 404 also refetches the session (status flips to ended). When the session leaves `active` (poll or 404), CallView refetches turns and traces once, since their polling stops with the status and their last fetch predates the final replies (found by the design review: a stale transcript after the call ends).
- **R4 `getFlows` follows `offset` in the one client function** (root cause for all seven callers: `ui/src/routes/{dashboard/DashboardView.tsx:54, flows/FlowsView.tsx:25, mcp/MCPView.tsx:25, onboarding/OnboardingView.tsx:60, providers/ProvidersView.tsx:146, sessions/CallView.tsx:42, sessions/CallsView.tsx:41}`), pages of 100 (the server max, `server/api/api.go:111-118`), stops at a short page, bounded by `FLOW_PAGES_MAX = 10` (1000 flows). The server orders by `id` (`server/storage/repositories.go:136`; flow ids are UUIDv7, so id order is creation order and new flows land on the last page), and a `limit` above 100 is a 400, not clamped (`server/api/api.go:115-117`). A flow created or archived between two page requests can shift offsets: the loop de-duplicates by `id` (a deletion can still skip one flow until the next refetch; said in the `ponytail:` comment). No `useFlows` hook (YAGNI: callers keep their queries).
- **R5 `bot-tts-text` is emitted from the pacer, after the unit's audio (revised after the design review).** What Pipecat does (non-word-timestamp TTS, `push_text_frames`): the TTS service pushes the `TTSTextFrame` **after** the unit's audio (`pipecat-impl/src/pipecat/services/tts_service.py:1433-1450`, the original pre-transform text, `:1437`); the observer handles it only when pushed from the `BaseOutputTransport` (`observer.py:452-456,515-519`), i.e. after the audio left the output transport, queued until `bot-started-speaking` (`:675-682`); an interruption flushes the transport queue, so the text of a cut unit is **dropped**; `bot-tts-stopped` goes out earlier, when the TTS service first pushes `TTSStoppedFrame`. Emitting at `TTSStoppedFrame` in the transport (the first draft) would instead send the text at synthesis completion, nearly always before playback, so a unit barged in mid-playback would already have sent all of it, and `ttsunit`'s error path calls `Finish()` for a partly heard unit (`core/ttsunit/ttsunit.go:221-223`), which would send the full text. **Decision (evidence):** the pacer already reports every successfully written frame, and never a flushed one, through `OnWriteComplete` (`transport/ws/pacing.go:621-625,668-671`, incl. the empty final marker; dropped frames skip it), and the transport's callback runs outside pacer locks and already writes RTVI from the pacer goroutine for speaking state (`transport/ws/transport.go:474-500`). So: `core.OutputAudioFrame` gains `Text string`, set by `ttsunit` only on the unit's **final** frame and only when the unit completed without a provider error; the transport's `OnWriteComplete` sends `bot-tts-text {"text": f.Text}` when `err == nil && f.IsFinal && f.Text != ""`. Result: after the unit's last audio is written (after `bot-started-speaking`; normally after `bot-tts-stopped`, as Pipecat — `bot-tts-stopped` is written when `TTSStoppedFrame` reaches the transport, which is right after the final frame is queued, so only an idle pacer that writes the final frame first can invert the two; declared as unspecified), dropped with a flushed unit, absent for a failed unit — no map, no extra state. Remaining declared differences: the text is the **cleaned** unit (`core/assistant_context.go:461-470`, `CleanTTSText`), not Pipecat's pre-transform text; a unit is a Switchboard sentence unit (merging rules in the parity matrix "Sentence/text aggregation"). No per-frame cost: one string header on a struct already allocated per frame, set only on finals. Word-level `bot-tts-text` (word-timestamp TTS) and `bot-output` (RTVI 2.x aggregate, `index.d.ts:548`) stay out of scope (Phase 8.4 matrix).
- **R6 Playwright determinism.** No `waitForTimeout` in new specs (existing `pace()` in `e2e/lib/mcp-helpers.ts:46` is not reused); every wait is an `expect(...)` on a visible state or `expect.poll` on the API. A second page in the same browser context holds the operator view while the first holds the call (`page.context().newPage()`; the key is per tab, so it signs in again).
- **R7 Route-mocked Playwright is acceptable only for states the echo stack cannot reach** without a server restart (7.2 `missing_env`), with the precedent `e2e/tests-flows/10-providers.spec.ts:26-43`; the request still goes through the real server and only the field is altered.
- **R8 Out of scope, carried:** `bot-output` and word-level TTS text (Phase 8.4 matrix); `turn_count`/"Turns" counting idle and greeting lines (Phase 6 behaviour change, documented in `docs/api/v1.md`; no UI relabel); flow version history UI beyond the editor's existing compare (B2, D-0.6).
